## 設計方針

- 決定: Gitのglobal ignoreを`~/.config/git/ignore`へ置き、
  `core.excludesFile`から明示参照する。
  - 根拠: repositoryごとのignoreへOS生成物とproject-local Claude stateを重複させない。
  - 依存する前提: `dot_config/git/ignore`がchezmoiで同じpathへ展開される。
  - 証拠: 一時repositoryでglobal file由来のignoreを確認した。
- 決定: `Advocate:` / `Challenger:` paneのClaude `Stop` / `StopFailure` hookが
  `herdr notification show`を直接実行する。
  - 根拠: 完了待機paneと`herdr agent wait`をなくし、reviewerのread-only tool集合を
    広げずに通知できる。
  - 依存する前提: reviewer paneへskillで定めたlabelをagent起動前に付ける。
  - 証拠: [ADR 0001](../adr/0001-herdr-adversarial-review.md)とhook fixture。

## 却下した代替案

- 案: reviewer promptへ通知commandの実行を指示する。
  - 利点: hook設定が不要。
  - 不採用理由: reviewerへBash toolを与え、inspect-only境界を弱める。
  - 再検討条件: Herdrがtool権限と独立したagent完了callbackを提供する場合。
- 案: coordinator paneで両reviewerの`done`を待つ。
  - 利点: 両者完了後に一つの通知へまとめられる。
  - 不採用理由: 待機paneとpolling commandが増え、main agentを自動再開するわけでもない。
  - 再検討条件: 一つの完了eventがmain agentを安全に再開できる場合。

## 2026-07-30 Adversarial / Sanity Review再設計

### 対話で確定した要件

- RulesとSkillsの構成は、AIが先に決めて実装せず、提案と合意を経て変更する。
- `conversation-context-export`と`sanity-review`は残す。
- contextはPRとSanity Reviewが設計変化、詳細な対話出力、実施内容、失敗、検証を追跡する
  証拠であり、完了時にも削減しない。
- reviewを複数のmodeとして一つのskillへ詰め込まない。一方、skillを小さくすること自体を
  目的にせず、責務が同じworkflowは一つのskillとして十分な内容を持たせる。
- 通常のreview段階は、DesignのAdversarial Reviewと、最後のAdversarial Reviewを含む
  Sanity Reviewの二つにする。各commitを対象にする独立した中間reviewは作らない。
- Design Adversarial Reviewでは、変更の必要性、過剰設計、より小さい案、誤った前提を
  実装前に争う。
- 現行agentが現在案の当事者なので、同じ立場を再構成するAdvocate agentは起動しない。
  現行agentへ対立するChallengerだけを1体起動する。
- Challenger専用tabは作らない。現行agentと同じHerdr tabのsibling paneへ起動する。
- 最終Sanity Reviewでは、Design段階のagentを再利用せず、最終成果物を対象にした
  Challengerを起動し、Sanity coordinatorが両段階の主張を一次証拠で検証する。

### 却下または修正した案

- 案: 作業途中に独立した中間Sanity Reviewを設ける。
  - 利点: Design後に変化した前提を早く発見できる。
  - 不採用理由: Designがmaterialに変わった場合はDesign Adversarial Reviewをやり直せば
    足り、通常段階を一つ増やす根拠にならない。
- 案: `design-sanity-review`を新設する。
  - 利点: Designと最終PRのreview名を分離できる。
  - 不採用理由: Designの必要性と過剰さを争う責務は既存`adversarial-review`で表現できる。
- 案: AdvocateとChallengerを2体起動する。
  - 利点: 二つの独立contextで両論を作れる。
  - 不採用理由: 現行agentがすでに採用案を作成しており、追加Advocateは同じ立場を重複して
    再構成する。
- 案: Challengerを専用background tabへ起動する。
  - 利点: main layoutを狭めず、未表示tabの完了を`done`として区別できる。
  - 不採用理由: Challenger 1体だけなら、同じtabのsibling paneでside-by-sideに監査できる。
    完了通知はClaude Stop hookが直接送るため、`done` stateを必要としない。
- 案: Designから最終まで同じChallengerを継続利用する。
  - 利点: incrementalな材料を渡せてstartupを省ける。
  - 不採用理由: Designへ形成した立場とcontextが最終成果物の独立したfirst passをbiasする。

### 確認したHerdrの事実

- Herdr skillは、明示指定がなければ現在tabのsibling paneと現在cwdを既定topologyにする。
- `herdr pane split --current --direction <right|down> --cwd "$PWD" --no-focus`でmainのfocusを
  維持してpaneを作成できる。
- 新規pane IDは作成responseの`.result.pane.pane_id`から取得し、表示順で推測しない。
- 同じ表示済みtabでは完了後のagent stateが`idle`になる場合がある。`idle`と`done`は
  settled stateとして結果取得の対象にできる。
- Claude `Stop` / `StopFailure` hookからのHerdr通知はagent stateと別経路なので、
  sibling paneでもpolling用paneや`agent wait` loopは不要である。

## 2026-07-30 ezaの壊れた動的link修復

### 発生した問題

- `eza -alF --icons --git`が起動時にabortした。
- `dyld`は`@rpath/libiconv.2.dylib`を
  `~/.local/share/mise/installs/clang/22.1.8/lib/`から探したが、対象fileは存在しなかった。
- 修復前の`otool -L`では、`eza`が`/opt`配下の旧brew-managed
  `libgit2.1.9.dylib`と`@rpath/libiconv.2.dylib`へ動的linkしていた。
- 修復前の`LC_RPATH`は、現在のmanifestで管理していない
  `~/.local/share/mise/installs/clang/22.1.8/lib`を指していた。

### 原因

- `cargo:eza`の既定buildは、build hostで検出したsystem `libgit2`を利用できる。
- このmachineで以前buildしたbinaryは、当時PATH上にあったmise管理clangと旧brew-managed
  `libgit2`を拾い、build環境固有の動的依存をbinaryへ残した。
- その後clangが管理対象外になって消えたため、同じversionの`eza`だけが削除済みtoolchainの
  RPATHを保持した。

### TDDと実装

- Red:
  - `scripts/ci/validate-mise.py`へportableなinstall sourceを要求する変更を先に追加した。
  - macOS標準`python3`は`tomllib`を持たず、最初の実行は
    `ModuleNotFoundError: No module named 'tomllib'`で失敗した。この失敗は期待したRedではない。
  - `UV_CACHE_DIR=/private/tmp/dotfiles-uv-cache uv run --offline --no-project --python 3.11`
    でvalidatorを実行し、旧manifestとの差分により期待どおり失敗することを確認した。
- 調査中の案:
  - `github:eza-community/eza`へ切り替え、`mise lock`で3 platformのassetを解決した。
  - Linuxは正しいbinaryを選んだが、macOSは`man-0.23.5.tar.gz`を誤選択した。
  - GitHub APIで公式`v0.23.5` releaseを確認するとmacOS binary自体が配布されていなかったため、
    この案と生成したlock entryを破棄した。
- 採用した実装:
  - `cargo:eza`へ`features = ["vendored-libgit2"]`を追加した。
  - repository validatorでmanifestとlock entryの同featureを必須化し、hostのsystem
    `libgit2`へ戻る変更を検出する。
  - mise公式Cargo backend仕様では`features`指定時にprebuilt installerをskipし、
    `cargo install --features`を使う。
